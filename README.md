# GSB Bugfix Task
## 题面
给一批水表电表做的 DTLS 接入网关这两个月一直不稳，现场反馈设备白天能上线，到了晚上就集体掉线。服务端回了 HelloRetryRequest 之后，客户端拿新的校验令牌重发 ClientHello，网关把两次请求当成两个独立握手，同一条五元组建出两份会话，设备侧收到两个 ServerHello 直接懵掉；这个令牌只按源 IP 生成，物业 NAT 出口下几百台设备共用一个地址，一台设备的重传能把另一台的握手顶掉；握手重传用固定一秒定时器，没按实际往返时延估算，卫星回传链路第三次重传就宣告失败；同一个 epoch 内记录乱序到达，重组窗口用后到的旧记录覆盖已经解密的新记录，抓包里能看到序号倒退；握手还没完成，客户端发来的应用数据就被直接送进业务层，早期数据的条数也没有上限；会话票据恢复只核对签名，跳过客户端证书有效期，过期的证书还能恢复出会话；密钥更新后旧 epoch 的记录仍然被接受，接收窗口没有随之上移关闭；压测时同一密钥下 nonce 出现重复，两条不同明文用了同一组密钥流；网关重启后校验令牌的密钥重新随机生成，正在握手的设备一起失败；分片握手消息的重组缓冲区没有硬上限，一个畸形客户端能把内存顶到几个 G；客户端证书链只验了叶子，中间证书缺失也放行；关闭通知发出后状态机停在 closing，文件描述符一直不回收，跑一天就报 too many open files。dtls_handshake_guard.py 的 DtlsHandshakeGuard 要把校验令牌和传输参数绑定，重传定时按往返估计退避，接收窗口按 epoch 隔离。硬性要求有四个：同一个令牌下重复的 ClientHello 并发进来也只能落成一条会话，第二个必须拿到明确拒绝；握手完成前收到应用数据必须回 unexpected_message 告警并丢弃；重启后令牌密钥要从落盘状态恢复，未完成的握手能接着走；关闭流程必须在有限步内释放套接字，不能停在 closing。test_dtls_handshake_guard.py 那十五项检查，从第一条起就没绿过。

## 运行方式
```bash
python -m pytest tests -q
```
